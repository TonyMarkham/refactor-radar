# Remaining Plan: Real LLM Brief Generation

## Current State

The current MCP implementation proves only configuration plumbing:

- `rr-mcp` accepts `--brief-model`.
- `rr-mcp` accepts `--max-concurrent-requests`.
- `generate_llm_brief` receives those values as defaults.
- `scan_project` can scan a single Rust crate and cache its SCIP model.

This does not satisfy the feature goal yet.

`generate_llm_brief` currently returns grounded evidence packets and prompt metadata. It does not call the configured model, does not generate final summaries, does not run concurrent LLM requests, and does not cache generated brief outputs.

## Feature Goal

`generate_llm_brief` should perform the second pass:

1. Select elements from the cached SCIP model.
2. Build grounded evidence packets for each selected element.
3. Send each evidence packet to the configured brief model.
4. Receive a generated 5W-style summary for each element.
5. Return generated summaries plus evidence/cache metadata.
6. Cache generated summaries by model, prompt version, and evidence hash.

The feature is not complete until at least one call to `generate_llm_brief` returns a summary generated by the configured model.

## Required Behavior

For each selected element, the tool should produce:

- `summary`: concise generated prose
- `five_w.who`
- `five_w.what`
- `five_w.when`
- `five_w.where`
- `five_w.why`
- `five_w.how`
- `unknowns`: unsupported or unavailable facts
- `evidence_hash`: copied from the evidence packet
- `cache_key`: copied from the evidence packet
- `generated_by_model`: the effective model used
- `prompt_version`: the prompt version used

The model must use only evidence from the evidence packet. Unsupported claims must become `unknown`, not invented facts.

## Configuration Rules

Effective values should resolve in this order:

1. Tool-call parameter
2. Server startup config
3. Hardcoded fallback

For `brief_model`:

- request `brief_model`
- server `brief_model`
- no fallback unless a project decision explicitly chooses one

For `max_concurrent_requests`:

- request `max_concurrent_requests`
- server `max_concurrent_requests`
- fallback `1`
- clamp minimum to `1`

## Cache Key

Generated summaries should be cached with this key:

```text
project_id
symbol_id
evidence_hash
prompt_version
brief_model
```

Value should include:

- generated summary payload
- evidence hash
- prompt version
- model
- generated timestamp or monotonic cache metadata if needed

Caching the model is valuable because the same evidence and prompt can produce different results from different models. The model must be part of the cache key.

## Implementation Steps

1. Add an LLM client boundary inside `rr-mcp` or a small supporting crate.

   The boundary should accept:

   - model name
   - prompt/instructions
   - evidence packet JSON
   - output schema expectation

   It should return typed generated brief data, not raw provider text.

2. Add typed MCP errors for LLM generation failures.

   Follow repository rules:

   - crate-local typed error variants
   - `thiserror`
   - `ErrorLocation`
   - `#[track_caller]` constructors
   - no `anyhow`

3. Add generated-brief data structs.

   These should represent the final output shape instead of passing unvalidated JSON through the code.

4. Update `generate_llm_brief`.

   The tool should:

   - build evidence packets as it does now
   - compute `evidence_hash`
   - check cache first
   - call the LLM client on cache miss
   - validate generated output
   - store generated output in cache
   - return generated summaries, not only evidence packets

5. Add concurrency.

   Use `max_concurrent_requests` to limit simultaneous LLM calls.

   The limit should apply only to model requests, not to local evidence-packet construction.

6. Preserve an evidence-only mode only if explicitly useful.

   If kept, it should be named clearly, for example:

   - `render_llm_inputs`
   - `dry_run`
   - `return_evidence_only`

   The default `generate_llm_brief` path must generate summaries.

7. Update MCP tests.

   Add a fake LLM client so tests do not call the network.

   Required test cases:

   - config model is used when request model is omitted
   - request model overrides config model
   - config concurrency is used when request concurrency is omitted
   - request concurrency overrides config concurrency
   - generated summary is returned
   - generated summary includes copied evidence hash
   - cache hit avoids a second LLM call
   - changed evidence hash causes a cache miss
   - different model causes a cache miss
   - invalid LLM response returns a typed MCP error

8. Add one manual smoke test path.

   After release build and restart:

   - scan `crates/rr-core`
   - call `generate_llm_brief` with `limit: 1`
   - omit `brief_model`
   - omit `max_concurrent_requests`
   - verify the response contains a generated summary from `gpt-5-mini`

## Verification Gate

Do not call the feature complete until all are true:

- `cargo test -p rr-mcp` passes
- `cargo test --workspace --all-targets` passes
- `cargo build --release -p rr-mcp` passes
- `target/release/rr-mcp --help` shows the config args
- MCP `initialize` succeeds with the configured args
- `generate_llm_brief` returns at least one generated summary
- the returned summary identifies `generated_by_model: gpt-5-mini`
- a repeated call with the same cache key avoids a second model call in tests

## Known Non-Goal

Returning evidence packets labeled with `brief_model` is not enough. That only proves plumbing. The remaining work is the actual LLM generation and generated-output cache.
